# 多模态情感计算系统 — 审核需求文档（MVA-Audit v0.1）

> 上游依据：`01-requirements.md`（业务需求）、`02-architecture.md`（五层架构）、`scripts/validate_real_data.py`（真实数据验证）。
> 本文不替代 `01-requirements.md`，而是为"端到端黑箱 → 模块可独立审计、失败可归因、改进可追踪"提供专项需求。
> 编号约定：`D-#` 数据层，`M-#` 模块层，`F-#` 失败归因层，`V-#` 可视化层，`I-#` 迭代闭环层，`L-#` 审核日志层。

---

## 0. 为什么要单独写这份需求

MVA 已通过 `validate_real_data.py` 跑通 6 项端到端验证（真实音频接入、跨模态融合、状态机闭环、隐私约束、跨会话记忆、行动层链路）。但**端到端绿 ≠ 每一层都准**。在向生产推进前，必须能回答三个问题：

| 业务问题 | 当前能否回答 | 本文要解决 |
|---|---|---|
| "某次错判到底是感知、快系统、融合、慢系统、记忆还是行动层出问题？" | 不能 | D / M / F |
| "如何量化每个模块的贡献，以便决定下一步改哪里？" | 不能 | M-2（消融）+ M-3（模态诊断） |
| "如何让一个非作者人员能在 10 分钟内看懂测试结果并批准发布？" | 不能 | V（可视化） + L（日志） |

本文将这三点做成**可被审计的工程产物**：固定输入契约 → 固定流水线 → 固定产物（`data/audit/` 下），不靠口述、不靠"看代码"。

---

## 1. 术语与边界

| 术语 | 定义 |
|---|---|
| **金标准（Gold Standard）** | 测试集的人工标注，包括：(a) 紧张度连续序列（0-1 滑条，1Hz）、(b) 模态标签（哪些模态"应当"被信任）、(c) 干预恰当性（1-5 分）、(d) 标注者 ID。 |
| **错误样本** | 端到端 fused stress 与金标准 stress 的绝对误差 > θ_err 的样本（默认 θ_err=0.20）。 |
| **失败归因** | 对每个错误样本，定位到一个**失败类型**。 |
| **审核会话（Audit Session）** | 一次完整审核流水线的执行单元：输入 = 测试集 + MVA 运行产物，输出 = `data/audit/<audit_id>/` 下的全部产物。 |
| **审核者（Reviewer）** | 人工修正/确认归因的人。每个修正都写日志（L-2）。 |

不在本文范围：
- 自动寻找最优模型（不是审核，是建模）
- 实时线上审核（本文只支持离线/回放）
- 对抗样本 / 安全测试（不在 MVA 业务定义内）

## 2. 数据层审核（D-#）

> 在评价模型之前，必须先确认测试数据本身可信。这一步被跳过是行业最常见的事故来源。

### D-1 标注一致性审核

情感标注天然主观。必须量化标注者间一致性。

| 指标 | 适用场景 | 可接受阈值 | 来源 |
|---|---|---|---|
| **Krippendorff α**（多标注者，多类别，可处理缺失） | ≥3 个标注者 / 任务 | α ≥ 0.67 可接受，α ≥ 0.80 良好 | Krippendorff 2013 |
| **Cohen κ** | 2 个标注者 | κ ≥ 0.60 可接受 | Cohen 1960 |
| **CCC**（Lin's Concordance Correlation） | 连续值标注 | CCC ≥ 0.80 | Lin 1989 |

**失败信号**：α < 0.67 → 标注不可信 → 必须**先回到 D-2 重新检视**，再进入 M 层。

### D-2 标注质量人工抽检

从测试集随机抽取 10% 样本，人工逐条检查：

| 字段 | 类型 | 说明 |
|---|---|---|
| `sample_id` | str | 样本 ID |
| `is_correct` | bool | 原标注是否正确 |
| `error_type` | enum | {类别错误, 强度错误, 边界模糊, 多模态不一致} |
| `error_reason` | enum | {标注者理解偏差, 数据本身模糊, 标注规范不清晰} |
| `corrected_label` | any | 修正后的标注（若有） |
| `reviewer_id` | str | 审核人 ID |
| `reviewed_at` | ISO 时间 | 审核时间 |

输出：`data/audit/<audit_id>/data_qa_report.md` —— 包含"模型犯错中多少比例是数据本身就错了"。

### D-3 数据分布审核

统计以下分布，**任一类别样本数 < 30 视为数据偏差**：

| 维度 | 统计项 | 失败信号 |
|---|---|---|
| 类别 | 每类样本数 + 占比 | 任一类别 < 30 |
| 强度 | 高/中/低强度样本数 | 极端强度 < 30 |
| 模态 | 每模态可用率 | 某模态 < 50% |
| 长度 | session 时长直方图 | < 1 min 或 > 60 min 占比异常 |

输出：`data/audit/<audit_id>/data_distribution.md`（含柱状图 ASCII 表）。

## 3. 模块级独立评估（M-#）

> 不要只评估端到端结果。逐模块独立评估是定位问题的核心方法。

### M-1 评估指标矩阵

| 模块 | 评估指标 | 评估方法 | 失败信号 |
|---|---|---|---|
| ① 感知（每模态） | 模态特征 vs 金标准模态标签的 CCC / 准确率 | 在带模态金标准的子集上独立跑 | 某模态 CCC < 0.5 |
| ② 快系统 | smoothed stress vs 金标准 stress 的 CCC、RMSE、MAE | 与金标准 stress 序列对比 | CCC < 0.5 / RMSE > 0.25 |
| ③ 慢系统 | state OK/WATCH/PAUSE vs 金标准状态的 F1 + 漏报率 | 与人工标注的"应当状态"对比 | 漏报率 > 30% |
| ④ 记忆 | 检索相关性的 Precision@K（人工评估） | 审核者对 top-3 检索结果各打 0/1 | P@3 < 0.5 |
| ⑤ 行动 | 干预恰当性的人工评分均值 | 1-5 分，李克特 | 均值 < 3.0 |

### M-2 消融实验（量化每个模块的贡献）

依次关闭/弱化每个模块，**保持其他模块不变**，记录端到端指标变化：

| 实验 | 配置 | 记录指标 |
|---|---|---|
| 完整 | 全部模块开启 | 基线 |
| 消融 P | 感知层只用 1 个模态（face / speech / text） | 模态消融 |
| 消融 F | 快系统 tau_fast → 0（不平滑） | 平滑贡献 |
| 消融 S | 慢系统不评估 | 慢系统贡献 |
| 消融 M | 记忆层不检索（不读历史） | 个性化贡献 |
| 消融 A | 行动层总是 continue | 行动层贡献 |

**贡献度 = 完整模型指标 − 消融后指标**。若某模块消融后指标几乎不变，说明该模块在当前任务中贡献有限。

### M-3 模态级诊断（破坏者识别）

借鉴 MIT Media Lab 的"模态破坏"框架：

1. 拆分：分别用 face / speech / text **独立**预测 stress。
2. 记录：每个模态的 (score, confidence)。
3. 对比：当融合结果与金标准不一致时，**检查哪个模态以高置信度输出了错误方向**。
4. 标记"破坏者"：若某模态的 confidence > 0.7 且 `sign(score - gold) != sign(fused - gold)`，则该模态为本次融合的破坏者。

输出：每个错误样本的 `modality_attribution` 字段，统计"破坏者是谁"。

## 4. 失败归因（F-#）

> 让 MVA 的每一个失败都变成可操作的改进线索，而非无法解释的黑箱输出。

### F-1 失败类型分类体系

| 失败类型 | 定义 | 定位到的模块 | 优先修复方向 |
|---|---|---|---|
| `perception_failure` | 某模态特征提取错误 | ① 感知 | 提升面部/语音特征 |
| `modality_sabotage` | 某模态高置信度错误主导融合 | ① 感知 + 融合 | 修改融合权重 / 加置信度校准 |
| `slow_eval_failure` | 慢系统状态机判断方向错误 | ③ 慢系统 | 优化预测器/评估器 |
| `memory_interference` | 检索到不相关的历史案例 | ④ 记忆 | 改检索相关性阈值 |
| `action_failure` | 干预策略与情境不匹配 | ⑤ 行动 | 调整策略生成逻辑 |
| `data_problem` | 金标准本身有误 | 数据层 | 修正标注或剔除样本 |
| `combined_failure` | 各模块单独看都合理，组合出错 | 融合逻辑 | 重新设计融合 |

### F-2 归因操作流程（按顺序排查）

```
对每个错误样本按下列顺序判定（首条命中即归因）：

  1. 检查金标准：
     人工重新审阅 sample 是否正确
     → 若标注有误 → data_problem

  2. 检查 M-3 破坏者结果：
     是否有模态 sabotage？
     → 是 → modality_sabotage

  3. 检查 M-1 各模态独立预测：
     某模态独立预测就是错的
     → 是 → perception_failure

  4. 检查慢系统输出 vs 实际状态：
     state 与金标准状态机不符
     → 是 → slow_eval_failure

  5. 检查记忆检索：
     检索到不相关历史案例
     → 是 → memory_interference

  6. 检查行动策略：
     干预动作与情境不匹配
     → 是 → action_failure

  7. 兜底：
     各模块单独看都"合理"但组合错
     → combined_failure
```

### F-3 量化归因结果

输出 `failure_distribution_report.md`：

| 失败类型 | 数量 | 占比 | 优先修复 |
|---|---:|---:|---|
| perception_failure | 45 | 30% | 提升感知层 |
| modality_sabotage | 30 | 20% | 修改融合 |
| ... | ... | ... | ... |

## 5. 可视化审核工具（V-#）

> 归因分析必须以可视化形式呈现，让审核者快速理解。

### V-1 单样本审核界面

对每个测试样本展示：

| 区域 | 内容 |
|---|---|
| 多模态输入 | 文本 / 语音波形图 / 面部关键帧缩略 |
| 各模态独立预测 | face→0.3, speech→0.7, text→0.5 |
| 融合结果 | 0.6 |
| 金标准 | 0.55 |
| 误差归因 | modality_sabotage: speech 高置信度错误 |
| 时间线 | 紧张度变化曲线，标峰值与转折点 |
| 人工修正区 | 审核者可下拉修改失败类型 + 备注 |

产物：`data/audit/<audit_id>/dashboard.html`（单页应用，< 5 MB）。

### V-2 批量审核仪表盘

| 视图 | 描述 |
|---|---|
| 混淆矩阵热图 | 哪些情感类别之间容易混淆 |
| 模态贡献分布 | 各模态在正确/错误样本中的贡献比例 |
| 失败类型分布饼图 | 7 类失败的占比 |
| 时间趋势图 | 每次迭代后各指标的变化 |
| 样本检索 | 按失败类型 / 模态 / 类别筛选样本 |

### V-3 跨迭代对比

每次审核的指标写回 `data/audit/_iterations.jsonl`，仪表盘自动绘制迭代趋势。

## 6. 迭代闭环（I-#）

> 审核的最终目的是驱动改进。必须形成"评估→归因→修复→再评估"闭环。

### I-1 修复优先级矩阵

按"占比 × 易修复"排序：

| 象限 | 条件 | 行动 |
|---|---|---|
| 高占比 + 易修复 | 例：modality_sabotage 30% + 调权重即可 | 立即处理 |
| 高占比 + 难修复 | 例：perception_failure 30% + 需换模型 | 长期计划 |
| 低占比 + 易修复 | 例：data_problem 13% + 标错 | 批量处理 |
| 低占比 + 难修复 | 例：combined_failure 8% + 需重构 | 暂缓 |

### I-2 修复效果验证

每次修复后重跑测试集，记录指标变化：

| 指标 | 修复前 | 修复后 | Δ |
|---|---:|---:|---:|
| 整体 CCC | 0.52 | 0.61 | +0.09 |
| 模态破坏数 | 30 | 18 | −12 |

若 Δ 与预期不符 → 归因判断有误 → 回到 F-2 重新分析。

### I-3 证据写回

每次评估的证据分三类写回 `data/audit/_evidence.jsonl`：

1. **任务正确性证据**：模型输出 vs 金标准
2. **过程合规性证据**：各模块是否按预期运行
3. **人工判断证据**：审核者修正

## 7. 审核日志与追溯（L-#）

> 每次审核操作都应可追溯，支持事后归因与问责。

### L-1 审核日志字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `log_id` | uuid | 唯一 |
| `audit_id` | str | 所属审核会话 |
| `reviewer_id` | str | 审核人 |
| `sample_id` | str | 被审核样本 |
| `system_attribution` | str | 系统自动归因 |
| `human_attribution` | str \| null | 人工修正（可为空） |
| `correction_reason` | str \| null | 修正理由 |
| `follow_up` | enum | {none, bug_filed, config_tuned, data_relabeled, ignored} |
| `timestamp` | ISO | 操作时间 |

存储：`data/audit/_audit_log.jsonl`（追加写，never overwrite）。

### L-2 审计链

每条样本可查到：

```
sample_id → error? → failure_type → reviewer_id → correction_reason → follow_up
```

支持事后归因：例如"v0.1.0 发布后的回归 → 哪些审核者当年同意过该样本"。

## 8. 验收标准（Acceptance Criteria）

一个审核会话"通过"必须满足：

- [ ] D-1 标注一致性 α ≥ 0.67（否则**不予进入 M 层**）
- [ ] D-2 人工抽检完成率 ≥ 10%
- [ ] D-3 分布报告无单类 < 30
- [ ] M-1 每个模块都有独立指标，且至少一个模块"红色"（否则说明测试集太弱）
- [ ] M-2 至少完成 P/F/S/M/A 5 个消融实验
- [ ] M-3 每个错误样本都有 modality_attribution
- [ ] F-1 每个错误样本都归到 7 类之一
- [ ] F-3 失败分布报告的 7 类占比之和 = 100%
- [ ] V-1 dashboard.html 存在且能在浏览器打开
- [ ] I-1 修复优先级矩阵生成
- [ ] L-1 _audit_log.jsonl 中至少有一条审核记录

## 10. 不做清单（Out of Scope）

- 自动化模型超参搜索（属于建模）
- 在线实时审核（本文只支持离线）
- 对抗样本 / 安全审计
- 跨被试泛化（每个新个体都需重审核）
- 标注者工作量分析（只量化一致性，不评估标注者水平）
